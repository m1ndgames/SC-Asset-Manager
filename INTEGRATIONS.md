# External Integrations — writing assets and trades from another program

SC-AssetManager is a fully client-side app. It has **no API and no server**, and it
never will — the SPA is static files served from a CDN.

That does not mean nothing else can write to it. When a user configures a sync
backend, **the backend _is_ the API**. An external program that authenticates as an
ordinary group member and writes to the same shared collections the app uses will
show up in every member's browser in real time, through the listeners the app
already runs (`src/lib/firestoreSync.ts`, `src/lib/pbSync.ts`). No polling, no
endpoint, no app change.

This document is the contract for doing that correctly. It is written so you can
implement a writer in any language without reading the app's source.

The motivating case — and the one the field notes below are drawn from — is a
**Game.log watcher**: a program that tails Star Citizen's log, detects commodity
trades, shows each one to the user for review and correction, and writes the
approved record into the backend.

> **Prerequisite.** A sync backend is required. In standalone mode all data lives in
> the browser's `localStorage` and is unreachable from outside. See
> [FIREBASE.md](FIREBASE.md) or [POCKETBASE.md](POCKETBASE.md).

## 1. Authenticating

Use a **normal group member account** — the same email/password the user signs into
the app with. Do not use a Firebase service account or a PocketBase admin token.
Attribution and the app's own permission checks are keyed to the signed-in member
(see §7), so a separate machine identity makes every record it writes unsellable
for a non-moderator.

### Firebase

```
POST https://identitytoolkit.googleapis.com/v1/accounts:signInWithPassword?key=<apiKey>
     {"email": "...", "password": "...", "returnSecureToken": true}
  -> { "idToken": "...", "refreshToken": "...", "expiresIn": "3600" }

POST https://securetoken.googleapis.com/v1/token?key=<apiKey>
     grant_type=refresh_token&refresh_token=<refreshToken>
```

`apiKey` is the `apiKey` from the Firebase web config the user pasted into Settings.
The `idToken` lasts one hour; refresh it.

Writes go to the Firestore REST API with `Authorization: Bearer <idToken>`:

```
PATCH https://firestore.googleapis.com/v1/projects/<projectId>/databases/(default)/documents/assets/<id>
```

> **Verify this yourself before relying on it.** A `PATCH` without an `updateMask`
> is a whole-document write, which is what the upsert semantics in §6 need — but
> confirm it against Google's current REST reference. Getting it wrong leaves stale
> fields on re-written records. If you are writing in JavaScript, use the Firebase
> SDK's `setDoc` instead and the question disappears.

`firestore.rules` allows any authenticated member to write `/assets` and `/trades`
regardless of role, so the writer account needs no role document seeded.

### PocketBase

```
POST <pbUrl>/api/collections/users/auth-with-password
     {"identity": "...", "password": "..."}
  -> { "token": "...", "record": { ... } }
```

Send the token as `Authorization: <token>`. Per POCKETBASE.md all CRUD rules are
`@request.auth.id != ""`.

## 2. Reference data the app publishes

Fetch these from the app's own host (e.g. `https://sc-assetmanager.org/...`). They
are regenerated by `scripts/fetch_items.py` whenever the game data is refreshed, so
reading them live keeps your writer current across game patches without a rebuild.

| File | Shape | Use |
|---|---|---|
| `/commodities.json` | `{ "<resourceGUID>": { "name": string, "key": string } }` | Turn a log line's `resourceGUID` into the exact string to put in `item` |
| `/items.json` | `{ name: string, type: string }[]` | The app's full item vocabulary; `type` is `commodity`, `ship`, `weapon`, … |
| `/locations.json` | `string[]` | Trading locations — present these as the picker for `location` / `sellLocation` |

**Every name in `commodities.json` is guaranteed to exist in `items.json` with
`type: "commodity"`.** The build unions them, so a GUID you can resolve is always a
name the app recognises. Use the `name` value verbatim: the app matches items by
display-name string, and a near-miss costs you the type badge, the type filter and
the UEX price lookup.

## 3. What the game log actually gives you

These are the two lines that matter, verbatim from a live 4.x log.

**Buy:**

```
<2026-11-01T09:11:29.754Z> [Notice] <CEntityComponentCommodityUIProvider::SendCommodityBuyRequest>
Sending SShopCommodityBuyRequest - playerId[214115750165] shopId[863690278779]
shopName[SCShop_Admin_lt_base_g] kioskId[863690278778] price[190453.000000]
shopPricePerCentiSCU[1.889409] resourceGUID[b999ef65-35be-45bf-908a-5eac6e06ba12]
autoLoading[1] quantity[100800.000000 cSCU] Cargo Box Data: boxSize[16.000000] | unitAmount[63]
```

**Sell:**

```
<2026-11-01T11:09:47.325Z> [Notice] <CEntityComponentCommodityUIProvider::SendCommoditySellRequest>
Sending SShopCommoditySellRequest - playerId[214115750165] shopId[862401115218]
shopName[SCShop_Admin_lt_base_g] kioskId[862401115214] amount[317120.000000]
resourceGUID[ea78052a-11b2-484e-a7ee-d19ed906a037] autoLoading[1] quantity[640]
transactionMode[ResourceContainer] Cargo Box Data:  [boxSize[8] | unitAmount[80]]
```

Things that will catch you out:

- **The unit differs between the two lines.** Buy `quantity` is in **cSCU**; sell
  `quantity` is in **SCU**. 1 SCU = 100 cSCU. In the examples above: 100 800 cSCU =
  1 008 SCU (and `boxSize` 16 × `unitAmount` 63 = 1 008 ✓), and the sell is 640 SCU
  (8 × 80 = 640 ✓). Cross-check against `boxSize × unitAmount` — it is a free
  parity check on your parser.
- **On a buy, prefer `shopPricePerCentiSCU` over `price`.** `price` is rounded to
  whole aUEC. `shopPricePerCentiSCU × 100` = 188.9409 aUEC/SCU, while
  `price / quantity` = 188.94147 — close, but the former is the real figure
  (188.9409 × 1008 = 190 452.43, which rounds to the logged 190 453).
- **On a sell there is no unit-price field.** Derive it: `amount / quantity`
  = 317 120 / 640 = **495.5** aUEC/SCU.
- **Success is never logged. Only failure is.** A successful transaction produces no
  confirmation line; a failed one produces
  `<CEntityComponentCommodityUIProvider::RmToken_CommodityTransactionResponse>` at
  `[Error]` level with `result[...]` and `type[Buying|Selling]`. So treat a request
  line as the trade, but **wait a couple of seconds for a following error line and
  discard the record if one arrives.**
- **There is no usable location in the log.** `shopName` is normally a generic
  template (`SCShop_Admin_lt_base_g`, identical at every admin office) and only
  occasionally location-bearing (`SCShop_AdminOffice_GrimHex`). The kiosk entity
  name (`..._kiosk_cordys_2_a-014`) is a **prefab** name and is identical at
  completely different stations — it is not a place. `shopId` and `kioskId` are
  per-session entity ids. Reverse-matching the price against UEX terminal data is
  unreliable because UEX prices are crowd-sourced.

  **Ask the user.** This is why a log watcher should be semi-automatic: show the
  parsed trade, let the user pick the location from `/locations.json`, and write only
  on approval.

## 4. `Asset` — the field contract

Source of truth: `src/lib/types.ts`.

| Field | Type | Req. | Notes |
|---|---|---|---|
| `id` | string | yes | UUID, lowercase, hyphenated. See §6. |
| `item` | string | yes | Display name. Use `commodities.json[guid].name` verbatim. |
| `amount` | number | yes | Quantity, **denominated in `unit`**. |
| `unit` | `"SCU"` \| `"cSCU"` \| `"μSCU"` | no | Absent = a plain unitless count. |
| `buyPrice` | number | yes | **aUEC per `unit`** — not per SCU. |
| `location` | string | yes | Where it was bought. Prefer a `/locations.json` value. `""` is legal and renders as `—`. |
| `quality` | number | no | 0–1000, commodities only. **The log does not provide it — omit the field rather than writing `0`.** |
| `createdAt` | string | yes | ISO 8601. |
| `loggedBy` | string | no | Nickname. See §7. |
| `source` | string | no | `"log-watcher"`. See §7. |
| `uexBuyId` | number | no | **Never set this.** Owned by the app's UEX push. |

**`amount` and `buyPrice` share one denominator.** This is the easiest thing to get
wrong, because the log hands you a price per *centi*-SCU. Two correct encodings of
the same purchase:

```jsonc
// recommended
{ "unit": "SCU",  "amount": 1008,   "buyPrice": 188.9409 }
// also correct
{ "unit": "cSCU", "amount": 100800, "buyPrice": 1.889409 }
```

**Prefer `SCU`.** The app seeds its sell modal's unit from `asset.unit`, the UEX push
converts to SCU anyway, and the portfolio total reads `amount * buyPrice` without
caring about units — so SCU is the form that behaves most naturally everywhere. Do
not round `buyPrice`.

> **`μSCU` starts with U+03BC GREEK SMALL LETTER MU**, not U+00B5 MICRO SIGN. They
> are visually identical and will not compare equal. Copy the codepoint, don't type
> the character.

## 5. `Trade` — the field contract

| Field | Type | Req. | Notes |
|---|---|---|---|
| `id` | string | yes | UUID. See §6. |
| `assetId` | string | yes | The `Asset.id` sold from. See §8 for sells with no asset. |
| `item` | string | yes | Copied from the asset. |
| `amountSold` | number | yes | Denominated in `unit`. |
| `unit` | CargoUnit | no | The **sell** unit. |
| `buyUnit` | CargoUnit | no | The unit `buyPrice` is denominated in. |
| `sellPrice` | number | yes | aUEC per `unit`. |
| `buyPrice` | number | no | aUEC per `buyUnit`. Omit if unknown. |
| `buyLocation` | string | no | Omit if unknown. |
| `sellLocation` | string | yes | Prefer a `/locations.json` value. |
| `soldAt` | string | yes | ISO 8601. |
| `loggedBy` | string | no | See §7. |
| `source` | string | no | `"log-watcher"`. |
| `uexSellId` | number | no | **Never set this.** |

**Set `unit` and `buyUnit` to the same value, or set neither.** The app's profit
column computes `(sellPrice - buyPrice) * amountSold` with **no unit conversion**, so
a record where `unit !== buyUnit` displays a wrong profit. The app itself can produce
such records (you may buy in SCU and sell in cSCU); a writer should not. For a
log-derived sell, `"SCU"` for both is correct.

`buyPrice` and `buyLocation` exist only to make the profit column work. When
`buyPrice` is absent or zero the Profit cell shows `—` and the record is excluded
from the P&L total. **If you don't know the buy side, omit both rather than writing
zeros** — a blank is honest, a zero reads as a 100 % margin.

## 6. Document ids and idempotency

### Where the id lives

**Firestore:** the document id and the `id` field must be identical. The app reads
records with `snapshot.data()` and discards the document id, then writes and deletes
by `doc(db, 'assets', record.id)`. A mismatch produces a record the app can display
but can never update or delete.

**PocketBase** cannot use a hyphenated UUID as a record id, so records carry both:

```
record.id     = toPbId(uuid)   // the PocketBase primary key
record.app_id = uuid           // the app's real id — readers prefer this
```

```
toPbId(uuid):
    s = uuid with all '-' removed            # 32 hex chars
    if s[0] is not a letter: s = 'r' + s     # PB ids must start with a letter
    return s
```

Always write both fields. `toPbId` is not reversible (the `r` prefix is
conditional), which is exactly why `app_id` exists.

### Deterministic ids

A log watcher will re-read lines it has already processed. Derive the id from the log
line instead of generating a random one, and every write becomes an idempotent
upsert.

Use **UUIDv5** (RFC 4122 §4.3, SHA-1) with a namespace derived from the app's domain,
so nothing has to be taken on trust:

```
NAMESPACE = uuid5(NAMESPACE_DNS, "sc-assetmanager.org")
          = c99fd589-c700-51a5-ac3b-1043be61f47f
```

The name string is `|`-joined, UTF-8, with no padding and no trailing separator:

```
"<kind>|<logTimestamp>|<resourceGUID>|<shopId>|<quantityRaw>"
```

- `kind` — literally `buy` or `sell`
- `logTimestamp` — the text **verbatim** between the leading `<` and `>` of the log
  line, e.g. `2026-11-01T09:11:29.754Z`. Do not reparse or reformat it; the
  millisecond precision is what makes the key unique.
- `resourceGUID`, `shopId` — verbatim bracket contents
- `quantityRaw` — **verbatim** text inside `quantity[…]`, with any trailing unit
  token and surrounding whitespace stripped: `100800.000000` for the buy above,
  `640` for the sell.

Keeping `quantityRaw` verbatim is deliberate. Parsing to a float and back gives
`100800.0` in Python and `100800` in JavaScript, which would silently break
idempotency across a rewrite in another language.

**Test vectors** — check your UUID library against these before going further:

| Name string | Expected id |
|---|---|
| `buy\|2026-11-01T09:11:29.754Z\|b999ef65-35be-45bf-908a-5eac6e06ba12\|863690278779\|100800.000000` | `4ed7a396-7398-590d-be1c-d3a012c0dcb6` |
| `sell\|2026-11-01T11:09:47.325Z\|ea78052a-11b2-484e-a7ee-d19ed906a037\|862401115218\|640` | `41604931-7f71-55f3-8059-77b46c7475b4` |

Output lowercase, hyphenated, canonical 36 characters — the same shape as the
`crypto.randomUUID()` the app generates, so nothing downstream can tell them apart.

**Two consequences worth understanding before you rely on this:**

1. The id is derived from the *request* line, not the outcome. A transaction that
   failed and was retried produces two request lines at two timestamps, hence two
   ids — which is correct, they were two attempts. Discard the failed one (§3)
   rather than trying to make the ids collide.
2. **A replay overwrites user edits.** If the user corrected a watcher-written record
   in the app and you then re-parse that log, your version wins. Track a high-water
   mark (last processed file offset or timestamp) and only replay deliberately.

## 7. Attribution and provenance

**`loggedBy`** should be **the user's own nickname** — the same one they set in the
app's Settings — not a separate `"watcher"` identity. This is not cosmetic: a member
with the `user` role can only sell assets whose `loggedBy` matches their nickname,
and the UEX push buttons are hidden on records logged by someone else. A distinct
identity would make everything the watcher writes unsellable and un-pushable for a
non-moderator.

**`source`** is how a record's origin stays visible once `loggedBy` is the user's own
name. Set it to `"log-watcher"`. The app shows a small `LOG` badge next to the item
name for any record that has it, which is what tells the user "the parser chose this
location, not me" the first time something lands in the wrong place.

Do not add further provenance fields (`shopId`, `kioskId`, `resourceGUID`,
`logTimestamp`). The deterministic id already encodes all of them, and anything else
can be re-derived from the log.

## 8. Buy and sell semantics

The app's own flows define these. Match them.

### A buy creates an `Asset`

Set `unit` (and omit `quality`, per §4). Then apply the app's **merge rule**: if an
asset already exists with the same `item` and the same `location`, add to its
`amount` rather than creating a second record. This keeps the inventory tidy across a
multi-stop run and matches what the user would get typing the purchase in by hand.

When you merge, compute a **quantity-weighted average** `buyPrice`:

```
newPrice = (oldAmount * oldPrice + addedAmount * addedPrice) / (oldAmount + addedAmount)
```

> The app's own manual merge simply **overwrites** `buyPrice` with the newest price,
> which destroys the cost basis across stops and makes the later profit figure wrong.
> Don't copy that behaviour; the weighted average is what the field is supposed to
> mean.

**Merging interacts with §6.** A merged asset's id is the *existing* asset's id, not
one derived from the new log line, so the merge itself is not idempotent — replaying
a log would add the quantity twice. Keep a high-water mark and do not replay merged
buys. If you would rather have strict replay safety than a tidy inventory, write one
asset per log line instead and let the user merge in the app.

### A sell creates a `Trade` and mutates the `Asset`

1. Convert the sell quantity into the **asset's** unit. The app pivots through μSCU:
   1 SCU = 1 000 000 μSCU, 1 cSCU = 10 000 μSCU. If the asset has no `unit`, no
   conversion happens and the quantity is used as-is.
2. Copy onto the trade: `assetId` = the asset's `id`, `item`, `buyPrice` =
   `asset.buyPrice`, `buyLocation` = `asset.location`.
3. Set `unit` to the sell unit and `buyUnit` to `asset.unit` — **both or neither**
   (§5).
4. Decrement the asset: `amount -= convertedQuantity`. **Delete the asset when the
   result is ≤ 0.** A partial sell leaves every other field untouched — `buyPrice`,
   `location`, `createdAt`, `loggedBy` and `uexBuyId` all survive.
5. Never write a negative `amount`. The app rejects an over-sell outright; a writer
   should clamp to what's available and show the discrepancy to the user instead.

**Write the `Trade` first, then mutate the `Asset`.** These are two separate writes
with no transaction. Crashing between them then leaves a trade whose asset wasn't
decremented — visible and correctable — rather than a vanished asset with no trade,
which is silent data loss.

### A sell with no matching asset

This happens whenever the user sells cargo the watcher never saw bought. It is
**safe**: `assetId` is write-only in this app. It is stored and round-tripped but
never dereferenced, and the trades table renders entirely from fields on the trade
itself. Edit and delete key off `trade.id`.

Recommended handling:

- Set **`assetId` to the trade's own `id`**. It is non-empty (PocketBase's schema
  wants a value), unique, deterministic, points at nothing, and self-documents the
  orphan condition without a magic sentinel.
- **Omit `buyPrice` and `buyLocation`**, so the Profit column honestly shows `—`.

Optionally your review UI can offer to back-fill a synthetic asset first so the trade
has a real parent and a real buy price. If you do, derive its id with a `backfill|…`
prefix so it stays idempotent.

## 9. Checklist

- [ ] Authenticate as the user's own member account, refresh the token
- [ ] Resolve `resourceGUID` via `/commodities.json`, use `name` verbatim
- [ ] Remember buy `quantity` is cSCU and sell `quantity` is SCU
- [ ] Use `shopPricePerCentiSCU × 100` for the buy price, `amount / quantity` for the sell
- [ ] Wait for, and discard on, a following `RmToken_CommodityTransactionResponse` error
- [ ] Get `location` from the user — it is not in the log
- [ ] `amount` and `buyPrice` in the same unit; `unit === buyUnit` on trades
- [ ] Deterministic UUIDv5 ids; verify against the test vectors in §6
- [ ] On PocketBase, write both `id` (`toPbId`) and `app_id`
- [ ] `loggedBy` = the user's nickname; `source` = `"log-watcher"`
- [ ] Never set `uexBuyId` / `uexSellId`
- [ ] Trade written before the asset is decremented
